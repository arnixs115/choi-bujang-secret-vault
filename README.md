# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 현재 단계: 2단계 — 자료를 코드 밖으로 옮기기

네 개의 가상 메모는 Supabase의 learning_notes 테이블에 저장합니다.
화면은 Vercel의 /api/notes 서버 함수를 통해 자료를 읽습니다.

서버 함수는 SUPABASE_URL과 서버 전용 SUPABASE_SECRET_KEY를

이후 단계에서 인증과 접근 제한을 적용해야 합니다.

## 3단계 — 로그인한 사용자만 내 자료를 다루게 합니다

### 구현 내용

Supabase Auth를 이용해 이메일/비밀번호 로그인을 추가하고, 로그인한 사용자의 access token을 `/api/notes` 요청에 전달하도록 구성했습니다.

서버에서는 기존 `src/verify-login.mjs`를 사용해 Supabase access token을 검증하고, 검증된 `userId`를 기준으로 메모의 소유자를 저장합니다.

#### 인증

- Supabase 공식 JavaScript SDK 사용
- 이메일/비밀번호 로그인
- 로그아웃
- 로그인 상태 확인
- 로그인한 사용자의 access token을 `Authorization: Bearer <token>`으로 API에 전달
- 서버에서는 브라우저가 전달한 사용자 ID가 아니라 `verify-login.mjs`가 검증한 `login.userId`를 사용

#### 메모 API

| Method | Route | 동작 |
|---|---|---|
| GET | `/api/notes` | 로그인한 사용자의 메모 목록 |
| POST | `/api/notes` | 로그인한 사용자의 메모 생성 |
| GET | `/api/notes/:id` | 특정 메모 조회 |
| PUT | `/api/notes/:id` | 특정 메모 수정 |
| DELETE | `/api/notes/:id` | 특정 메모 삭제 |

POST 요청은 `{ id, title, body }` 형식을 사용하며, `id`가 없으면 서버에서 UUID를 생성합니다.

DB에는 다음과 같이 저장합니다.

- `id`: UUID
- `owner_id`: 서버에서 검증한 로그인 사용자 ID
- `title`: 메모 제목
- `content`: 메모 본문

API에서는 DB의 `content`를 클라이언트의 `body`로 변환합니다.

### 보안 관련 설정

`aleph.config.json`의 `allowedRoutes`에 실제 메모 API 경로를 등록했습니다.

```json
[
  "GET /api/notes",
  "POST /api/notes",
  "GET /api/notes/:id",
  "PUT /api/notes/:id",
  "DELETE /api/notes/:id"
]
```

서버 전용 `SUPABASE_SECRET_KEY`는 브라우저 코드에 포함하지 않고 Vercel 환경변수로 관리합니다.

브라우저에서는 Supabase URL과 Publishable Key만 사용합니다.

### 현재 단계에서 의도적으로 남겨둔 부분

현재 `GET /api/notes` 목록 조회와 메모 생성에는 `owner_id`를 적용했습니다.

반면 개별 메모의 `GET /api/notes/:id`, `PUT /api/notes/:id`, `DELETE /api/notes/:id`에서는 아직 메모 소유자 검사를 하지 않습니다.

따라서 현재 단계에서는 메모 ID를 알고 있는 다른 사용자가 해당 메모를 조회하거나 수정 또는 삭제할 수 있는 문제가 남아 있습니다.

이 문제는 다음 단계에서 **BOLA/IDOR 형태의 객체 소유권 검증 문제**로 확인하고 수정합니다.

### 재현 / 확인 방법

1. 정상 사용자로 로그인합니다.
2. 메모를 추가하고 수정 및 삭제합니다.
3. 로그아웃하거나 시크릿 창에서 `/api/notes`를 요청합니다.
4. 인증되지 않은 요청이 `401` JSON 응답으로 거부되는지 확인합니다.
5. 배포 주소의 `/aleph.json`이 정상적으로 열리는지 확인합니다.
6. `/` 응답의 보안 헤더를 확인합니다.

### 다음 단계

**4단계 — 로그인해도 내 자료만 보이게 합니다**

개별 메모 API에도 `owner_id` 검사를 적용하여, 다른 사용자가 메모 ID를 알고 있더라도 조회·수정·삭제할 수 없도록 변경합니다.

## 4단계 — 다른 사용자의 메모에 접근하지 못하게 하기

### 목표

3단계에서는 로그인한 사용자만 메모 API를 호출할 수 있도록 인증을 추가했습니다. 하지만 개별 메모 API에서 소유자를 확인하지 않으면 다른 사용자의 메모 ID를 알아낸 사람이 해당 메모를 조회하거나 수정 또는 삭제할 수 있습니다.

4단계에서는 **메모 ID뿐 아니라 로그인한 사용자의 소유권까지 확인**하도록 API를 수정하고, Supabase 데이터베이스에도 RLS(Row Level Security) 정책을 설정합니다.

### 구현 내용

#### 1. API의 메모 소유권 검사

`src/verify-login.mjs`를 통해 검증한 로그인 정보에서 `login.userId`를 가져와 메모의 `owner_id`와 비교하도록 수정했습니다.

| Method | Route | 소유권 검사 |
|---|---|---|
| GET | `/api/notes` | 목록 조회 시 `owner_id` 필터 적용 |
| POST | `/api/notes` | 서버에서 검증한 사용자 ID를 `owner_id`로 저장 |
| GET | `/api/notes/:id` | 메모 ID와 `owner_id`를 함께 확인 |
| PUT | `/api/notes/:id` | 메모 ID와 `owner_id`를 함께 확인 |
| DELETE | `/api/notes/:id` | 메모 ID와 `owner_id`를 함께 확인 |

메모를 수정하거나 삭제할 때 클라이언트가 전달한 ID만으로 대상을 선택하지 않습니다. 로그인한 사용자가 소유한 메모에만 작업을 수행하도록 조건을 추가했습니다.

소유자가 아닌 사용자의 메모를 조회·수정·삭제하려고 하면 `404 NOTE_NOT_FOUND` 응답을 반환해 해당 메모를 작업 대상으로 찾을 수 없도록 처리합니다.

메모 생성 시에도 클라이언트가 보낸 `owner_id`를 신뢰하지 않고, 서버에서 검증한 로그인 사용자 ID를 사용합니다.

이러한 검사는 객체의 ID를 이용해 다른 사용자의 데이터에 접근하는 **BOLA/IDOR 유형의 접근 제어 취약점**을 방지하기 위한 것입니다.

#### 2. Supabase RLS 및 테이블 권한 설정

`public.learning_notes` 테이블에 RLS를 활성화하고, 사용자별 소유권을 확인하는 정책을 설정했습니다.

- **SELECT:** 본인이 소유한 메모만 조회
- **INSERT:** 본인의 사용자 ID가 `owner_id`에 지정된 메모만 생성
- **UPDATE:** 본인이 소유한 메모만 수정하고, 수정 후에도 소유권 조건 유지
- **DELETE:** 본인이 소유한 메모만 삭제

정책의 소유권 조건은 `auth.uid() = owner_id`를 기준으로 합니다. INSERT 정책은 `WITH CHECK`, SELECT와 DELETE 정책은 `USING`, UPDATE 정책은 두 조건을 함께 사용합니다.

또한 `learning_notes` 테이블에 대한 권한을 확인하고, `anon` 및 `authenticated` 역할의 테이블 권한을 필요한 범위로 제한하도록 설정했습니다.

> **주의:** 현재 서버 API는 서버 전용 `SUPABASE_SECRET_KEY`로 데이터베이스에 접근합니다. 이 키는 RLS를 우회할 수 있으므로, API 요청의 사용자 간 접근을 막는 데에는 서버 코드의 소유권 검사가 중요합니다. RLS 정책의 실제 강제 여부는 일반 사용자 인증 정보로 직접 데이터베이스에 접근하는 별도 테스트로 확인해야 합니다.

위의 미완료 항목은 실제 테스트 결과를 확인한 뒤 체크합니다. 정책이 존재한다는 사실만으로 사용자 간 접근 차단이나 권한 설정이 모두 검증된 것은 아닙니다.

### 재현 및 검증 방법

1. 사용자 A와 사용자 B로 각각 로그인해 테스트 메모를 생성합니다.
2. 각 메모의 ID를 기록합니다. 실제 개인정보 대신 가상 메모를 사용합니다.
3. 사용자 A의 인증 정보로 사용자 B의 메모 ID에 대해 GET 요청을 보냅니다.
4. 같은 방식으로 PUT 및 DELETE 요청을 시도합니다.
5. 사용자 B로 로그인해 원래 메모가 변경되거나 삭제되지 않았는지 확인합니다.
6. 메모 생성 요청에 임의의 `owner_id`를 넣어도 서버에서 검증한 사용자 ID로 저장되는지 확인합니다.
7. Supabase에서 RLS 활성화 여부, 정책 조건, 역할별 테이블 권한을 별도로 확인합니다.

테스트할 때 `Authorization` 헤더의 Bearer 토큰은 외부에 공유하거나 README에 기록하지 않습니다.

### 보안 개선 결과

## 5단계 — 브라우저의 Supabase 직접 호출 제거

### 목표

기존에는 브라우저에서 Supabase JavaScript SDK를 직접 불러와 이메일·비밀번호 로그인을 처리했습니다.

5단계에서는 로그인 요청을 Vercel 서버리스 API로 전달하도록 변경하여, 브라우저와 Supabase 사이의 직접적인 인증 호출을 제거합니다. 기존 메모 API와 사용자별 소유권 검사는 유지합니다.

### 구현 내용

#### 1. 서버 로그인 API 추가

`api/auth/login.js`를 추가해 로그인 처리를 서버에서 수행하도록 구성했습니다.

- `POST /api/auth/login`으로 이메일과 비밀번호를 전달합니다.
- 서버에서 `SUPABASE_URL`과 `SUPABASE_PUBLISHABLE_KEY` 환경변수를 사용해 Supabase Auth에 인증을 요청합니다.
- 인증 성공 시 access token, 만료 시각, 사용자 정보를 반환합니다.
- 잘못된 로그인 정보는 `401 LOGIN_FAILED`로 처리합니다.
- 필수 환경변수가 없으면 `500 SUPABASE_AUTH_CONFIG_MISSING`을 반환합니다.
- POST 이외의 요청은 `405 METHOD_NOT_ALLOWED`로 거부합니다.

#### 2. 브라우저 로그인 코드 변경

- 로그인 요청을 `/api/auth/login`으로 전달합니다.
- 로그인 세션을 `sessionStorage`에 저장합니다.
- 로그아웃 시 저장한 세션을 제거합니다.
- 세션의 access token을 기존 메모 API 요청에 Bearer 토큰으로 전달합니다.

#### 3. 기존 메모 API 유지

기존 `/api/notes` 및 `/api/notes/:id` API를 유지해 메모 조회·생성·수정·삭제 기능이 기존 인증 및 소유권 검사 구조를 계속 사용하도록 했습니다.

서버 전용 `SUPABASE_SECRET_KEY`는 계속 Vercel 환경변수로 관리하며, 브라우저 코드에 포함하지 않습니다.

## 보너스 XDR 1 — 무차별 대입 공격을 탐지하고 대응안을 생성합니다

### 목표

5단계까지는 로그인과 자료 API의 인증 및 접근 제어를 개선했습니다.

XDR 1에서는 로그인 실패 이벤트를 분석해 무차별 대입(Brute-force) 공격 가능성을 판단하고, 판단 결과에 따라 대응 단계를 구분하도록 구성합니다.

모든 이벤트를 무조건 공격으로 취급하지 않고, 명확한 공격과 추가 확인이 필요한 시도, 정상 이벤트를 구분하는 것을 목표로 합니다.

### 구현 내용

#### 1. 공격 이벤트 분류

`xdr/fixtures/brute-force.json`에 정의된 가상 보안 이벤트를 입력으로 사용합니다.

`xdr/brute-force/decide.mjs`에서 이벤트의 다음 정보를 바탕으로 공격 가능성을 판단합니다.

- 로그인 실패 횟수
- 이벤트 설명에 포함된 공격 징후
- 출발지 IP 주소
- 탐지 규칙의 심각도
- MITRE ATT&CK 기법 정보(T1110)

판단 결과는 신뢰도 점수와 사유를 포함하며, 점수에 따라 다음 세 가지 조치로 분류합니다.

| 조치 | 의미 |
|---|---|
| `block` | 명확한 공격 징후가 있어 차단 대상으로 판단 |
| `alert` | 공격 가능성이 있어 추가 확인이 필요함 |
| `record` | 명확한 공격 패턴이 없어 기록 대상으로 분류 |

#### 2. 대응안 생성

`xdr/brute-force/respond.mjs`를 통해 탐지 결과를 후속 대응 단계로 전달합니다.

대응 과정에서는 이벤트와 판단 결과를 기록하고, 차단이 필요한 이벤트에 대해 차단 규칙 제안안을 생성하도록 구성합니다.

차단 규칙 제안은 실제 네트워크나 ZTNA 정책에 적용된 차단과 구분합니다. 제안안이 생성되었다는 사실만으로 공격 트래픽이 실제로 차단되었다고 판단하지 않습니다.

#### 3. 실행 결과 생성

실행 명령어는 다음과 같습니다.

```bash
npm run xdr:run -- brute-force
```

분류 결과는 `xdr/brute-force/result.json`에 저장됩니다. 결과 파일을 통해 각 이벤트의 조치, 신뢰도, 판단 사유 및 전체 조치별 건수를 확인할 수 있습니다.

### 검증 방법

```bash
npm run xdr:run -- brute-force
node -e "const r=require('./xdr/brute-force/result.json'); console.log(r.counts); console.log(r.decisions.map(x=>x.alertId+': '+x.action).join('\n'))"
```

실행 결과를 평가기에 제출해 공격 차단, 애매한 시도 알림, 정상 이벤트 기록이 의도대로 구분되는지 확인합니다.

- [x] `block`, `alert`, `record` 세 가지 조치 구분
- [x] 판단 결과를 JSON 파일로 생성

## 7단계 — 복합 이상 접속에 추가 확인을 적용합니다

### 목표

평소와 다른 시각, 낯선 네트워크, 짧은 시간 동안 발생한 대량 자료 접근이 함께 나타나는 가상 사건을 탐지하고, 정상 요청과 구분해 추가 확인(`step_up`)을 요구하도록 판정 규칙을 추가했습니다.

특정 지역 정보 하나만으로 영구 차단하지 않고, 여러 신호가 동시에 충족되는지를 확인하도록 구성했습니다.

### 구현 내용

#### 1. 복합 이상 접속 판정 규칙 추가

`src/decider.mjs`에 다음 조건을 함께 확인하는 규칙을 추가했습니다.

- 접속 시각이 06시 이전 또는 22시 이후
- 네트워크 신호가 `unusual`
- 최근 300초 이내에 `risk_signal` 이벤트가 10회 이상 발생

세 조건이 모두 충족되면 추가 확인을 요구합니다. 기존 등록 기기 검사와 정상 자료 조회 규칙은 유지했습니다.

추가 확인 이후의 허용 여부는 재인증 정보와 자료 조회 경로를 확인하도록 구성했습니다. 다만 판정 요청의 `stepUp` 값만으로 동일 계정의 새 로그인 여부가 입증되는 것은 아니므로, 실제 재인증 검증과 연결되는지는 별도로 확인해야 합니다.

#### 2. 가상 사건 테스트

다음 명령으로 가상 요청에 대한 판정 결과를 확인했습니다.

브라우저 개발자 도구의 Network 탭에서 재인증 후 새로운 `login` 요청과 `notes` 요청이 발생하는 것을 확인했습니다.

- 응답: 자료 반환
- 요청 발생 시점: 로그인 이후
- Vercel 로그: 확인 당시 새로운 로그가 추가되지 않음

따라서 재인증 이후 브라우저에서 새 자료 요청이 발생하고 정상 응답을 받은 사실을 확인했습니다.

## 8단계 — 자료 API에서도 사용자 권한을 검증합니다

## 9단계 — 폭주 조회를 탐지하고 회수 제안을 생성합니다

### 목표

정상적인 자료 조회와 짧은 시간 동안 발생한 대량 조회를 구분하고, 폭주 조회가 확인된 경우 회수 제안을 반환하도록 구성했습니다.

단순히 전체 요청 수만 세지 않고, 같은 사용자의 GET 요청이 10분 이내에 120건을 초과하는지 확인합니다. 서로 다른 사용자의 요청을 합산하거나 10분 밖으로 흩어진 요청을 하나의 폭주로 판단하지 않습니다.

이번 단계에서는 탐지 결과를 제안하는 기능만 구현하며, 실제 접속 회수 API를 호출하거나 기기의 권한을 변경하지 않습니다.

### 구현 내용

#### 1. 폭주 조회 탐지 규칙 추가

`src/detect.mjs`의 `detect(events)`에 폭주 조회 탐지 규칙을 추가했습니다.

탐지 규칙은 다음과 같습니다.

- 같은 `identity.sub`의 GET 요청을 사용자별로 구분합니다.
- 요청 시각을 기준으로 10분 이내의 조회 건수를 확인합니다.
- 같은 사용자의 GET 요청이 10분 안에 120건을 초과하면 폭주 조회로 판단합니다.
- 정상 조회이거나 폭주 조건을 충족하지 않으면 관찰 결과를 반환합니다.

정확히 120건인 경우에는 회수 제안을 생성하지 않습니다. 121건부터 폭주 조회로 분류합니다.

#### 2. 탐지 결과 형식 제한

폭주 조회로 판단하면 다음 세 키만 반환하도록 구성했습니다.

```js
{
  action: 'propose_revocation',
  reasonCode: 'burst_read',
  subject: '해당 sub'
}
```

폭주 조회 조건을 충족하지 않으면 다음 결과만 반환합니다.

```js
{ action: 'observe' }
```

응답에 기기 번호 등의 추가 키를 포함하지 않으며, 기존 `src/decider.mjs`의 허용·거부 응답 형식은 변경하지 않았습니다.

#### 3. 가상 사건 테스트

다음 명령으로 폭주 조회 탐지 규칙을 확인했습니다.

```bash
npm run detect:test
```

## 10단계 — 정책 사본을 검증하고 특정 메모의 복구 안전성을 확인합니다

### 목표

복구 작업이 잘못된 정책 사본이나 다른 사용자의 데이터에 영향을 주지 않도록, 복구 전에 정책 사본을 검증하고 지정한 메모 한 건만 복구하도록 구성했습니다.

복구 대상의 ID, 소유자, 내용 해시를 기준으로 복구 결과를 검증하며, 검증에 실패하거나 필요한 사본이 없으면 복구를 진행하지 않는 것을 목표로 합니다.

### 1. 복구 직전 정책 사본 검증

복구를 실행하기 전에 정책 사본을 다시 읽어 검증합니다. 검증 결과와 복구로 변경될 항목을 먼저 보여 준 뒤에만 복구를 호출합니다. 검증에 필요한 사본이 없거나 검증에 실패하면 복구를 중단하며, 이 경우 복구 경로를 호출하지 않습니다.

#### 실행 순서

1. **정책 사본 다시 읽기**
   - 복구 실행 직전에 사용할 정책 사본을 다시 읽습니다.
   - 사본이 존재하고 정상적으로 읽히는지 확인합니다.
   - 사본이 없거나 읽을 수 없으면 즉시 중단합니다. 복구 경로를 호출하지 않습니다.

2. **버전 검증**
   - 사본의 버전을 확인합니다.
   - 복구 대상에 적용할 수 있는 버전인지 확인합니다.
   - 버전을 확인할 수 없거나 검증에 실패하면 중단합니다. 복구 경로를 호출하지 않습니다.

3. **무결성 검증**
   - 사본의 무결성을 검증합니다.
   - 검증 결과가 일치하지 않거나 무결성을 확인할 수 없으면 중단합니다. 복구 경로를 호출하지 않습니다.

4. **변경 범위 확인**
   - 사본을 적용했을 때 변경될 정책 항목을 확인합니다.
   - 실제 운영 정책은 변경하지 않는 것을 원칙으로 합니다.
   - 변경 범위를 확인할 수 없거나 허용되지 않은 변경이 포함되면 중단합니다. 복구 경로를 호출하지 않습니다.

5. **복구 전 미리보기**
   - 복구를 실행하기 전에 검증한 사본의 버전, 무결성 검증 결과, 변경될 항목을 먼저 보여 줍니다.
   - 미리보기 내용을 확인할 수 없는 경우에도 복구를 진행하지 않습니다.

6. **복구 호출**
   - 위 검증을 모두 통과하고 미리보기까지 확인한 경우에만 복구 경로를 호출합니다.
   - 검증 단계 중 하나라도 실패했거나 사본이 없으면 복구를 호출하지 않습니다.

#### 확인 상태

- [ ] 복구 직전에 정책 사본을 다시 읽음
- [ ] 사본의 버전을 검증함
- [ ] 사본의 무결성을 검증함
- [ ] 변경 범위를 확인함
- [ ] 복구 전에 버전·검증 결과·변경 항목을 미리보기로 표시함
- [ ] 사본 누락 또는 검증 실패 시 복구 경로가 호출되지 않는지 확인함
- [ ] 실제 운영 정책이 변경되지 않는지 확인함

#### 2. 구성 요소

**학생 판정기** (`src/decider.mjs`, `decide(request)`): 엔진이 확인한 요청을 받아 `allow`, `deny`, `step_up` 중 하나를 응답 다섯 항목으로 돌려줍니다. 규칙 이름(`RULE_IDS`)은 네 개입니다.

| 규칙 | 동작 |
|---|---|
| `starter.deny` | 요청·신호·최근 사건의 형식이 계약과 다르면 `deny`(`starter_not_ready`) |
| `device_registered` | `deviceRegistered`가 `true`가 아니면 `deny`(`device_not_registered`) |
| `resource_zone_policy` | 메모는 `GET /notes/:id`, `POST /notes/:id/restore`만, 공지는 읽기만 허용. 목록·강사 자료·알 수 없는 서비스는 `deny` |
| `step_up_required` | 비정상 시간(6시 전·22시 이후), 비정상 네트워크, 최근 5분 안 위험 신호 10건 이상이 모두 겹치면 `step_up`. 5분 안에 재인증했고 `GET`이면 `allow` |

**탐지 규칙** (`src/detect.mjs`, `detect(events)`): 같은 `identity.sub`의 `GET` 사건이 어느 10분 구간에서든 120건을 넘으면 `propose_revocation`(`burst_read`)을, 아니면 `observe`를 돌려줍니다. 이것은 **회수 제안**이며 접속을 실제로 끊는 일은 엔진이 합니다. XDR 보너스 `xdr/brute-force/decide.mjs`는 가상 경보를 `block`·`alert`·`record`로 나누고, `respond.mjs`는 차단 규칙 **제안**만 만듭니다. 제안이 실제 차단은 아닙니다.

**접속 앱** (Vercel): `public/`의 정적 화면과 `api/`의 서버 함수입니다.

| 경로 | 역할 |
|---|---|
| `POST /api/auth/login`, `POST /api/auth/logout` | 서버를 거치는 로그인과 로그아웃(로그인 쿠키·기기 세션 쿠키 삭제, 기기 세션 회수) |
| `GET·POST /api/notes`, `GET·PUT·DELETE /api/notes/:id` | 내 메모. 로그인과 승인된 기기 세션이 모두 필요 |
| `POST /api/notes/:id/restore` | 지정한 스냅샷으로 메모 한 건 복구 |
| `POST /api/device/status` 외 4개 | 기기 등록·인증(WebAuthn)과 상태 조회 |
| `/api/ai`, `/api/threat-intel` | 시작 틀의 미구현 뼈대(항상 501) |
| `GET /attack-results.json` | 작전실이 읽는 정적 결과 파일. 점검기가 실제로 요청을 보내 만든 것만 담으며, 파일이 없으면 작전실은 숫자 없이 "실행한 점검 결과가 없습니다"를 표시 |

**자료실** (Supabase): 코드가 읽고 쓰는 테이블은 `learning_notes`, `device_credentials`, `device_sessions`, `device_challenges`이고, 복구는 DB 함수 `restore_learning_note_snapshot`을 부릅니다. **테이블·함수를 만드는 SQL은 이 저장소에 없습니다.** Supabase 화면에서 만든 것이므로, 새 프로젝트에서는 같은 구조를 직접 만들어야 하며 그 절차는 이 저장소만으로 재현되지 않습니다.

1. 저장소를 받고 검사한 커밋으로 맞춥니다: `git clone <저장소 주소>` 후 `git checkout <검사한 커밋>`.
2. `npm ci`로 의존성을 설치합니다.
3. Vercel에서 이 저장소로 새 프로젝트를 만듭니다. 빌드 명령은 `vercel.json`의 `npm run build`입니다. 이 빌드는 Vercel이 주는 저장소·커밋·배포 주소가 없으면 일부러 실패합니다.
4. Vercel의 **환경변수 비밀 입력란**에 아래 이름으로 값을 넣습니다. 값은 이 문서, Git, 로그, 캡처에 남기지 않습니다.

| 이름 | 용도 | 값을 받는 곳 |
|---|---|---|
| `SUPABASE_URL` | Supabase 프로젝트 주소 | Supabase 프로젝트 설정 |
| `SUPABASE_PUBLISHABLE_KEY` | 로그인 API가 쓰는 공개용 키 | Supabase API 키 화면 |
| `SUPABASE_SECRET_KEY` | 서버 함수 전용 키. 브라우저·응답·Git에 넣지 않음 | Supabase API 키 화면 |

`SUPABASE_SECRET_KEY`가 없으면 메모·기기 API가 정상 동작하지 않습니다(로그인 검증기를 만들지 못함).
5. `aleph.config.json`을 배포와 대조합니다: `publicAppUrl`, `repoUrl`, `identityProvider`, `allowedRoutes`, `originalApiUrl`. **`judgeIssuer`는 운영 측이 채운 값이므로 바꾸지 않습니다.**
6. 기기 승인: 화면에서 `이 기기 등록 요청`을 누르면 자격 증명이 `pending`으로 저장됩니다. 관리자가 Supabase에서 `device_credentials`의 `status`를 `approved`로 바꾸고 `approved_by`, `approved_at`을 채워야 합니다. 셋 중 하나라도 없으면 승인으로 보지 않습니다.

```bash

npm run test:r5

```

배포한 앱에 대한 실제 점검. 점검기는 **GET만** 보냅니다(세션 값이 없으면 로그인 없는 GET 9건). POST·PUT·PATCH·DELETE가 필요한 시험은 보내지 않고 `not_run`으로 남깁니다:

```bash
node -e "import('./src/attack-check.mjs').then(async m=>console.table((await m.runAttackChecks(JSON.parse(require('fs').readFileSync('aleph.config.json')))).map(r=>({id:r.testId,status:r.status,http:r.httpStatus,rid:r.requestId}))))"
```

승인된 기기 세션이 필요한 정상 요청은 `ATTACK_CHECK_LOGIN_TOKEN`, `ATTACK_CHECK_DEVICE_TOKEN`을 **학생이 직접** 환경에 넣었을 때만 보냅니다. 없으면 `not_run`으로 남습니다. 이 값은 기록·출력되지 않습니다.

작전실에 보일 결과 파일은 같은 점검기를 실행해 `public/attack-results.json`으로 저장합니다(아래 5-1절): `npm run attack:results`.

제출 묶음은 `npm run bundle`로 만듭니다. 형식은 채점표가 읽는 `aleph.defense.submission.v2`이며, 점검 결과는 `attackAttempts`(`attackId`·`expected`·`observed`, 최대 20개)로 들어갑니다. `observed`에는 실제로 받은 HTTP 상태 코드 숫자만(`401` 등) 적고, 심판 메모에서 요청 기록이 없다고 지적된 6건(`SENT_BUT_UNCONFIRMED`, 요청은 보냈고 응답은 점검 결과 파일에 그대로 남음)과 요청을 보내지 않은 시험과, 시도했으나 HTTP 응답을 받지 못해 확인된 상태가 없는 시험은 `not_run`입니다(후자는 점검 결과 파일에는 `httpStatus: null`인 실패로 남습니다). 20개를 넘는 시험표는 실제로 보낸 시험을 먼저 넣고, 보낸 시험이 없는 단계(6·7·9단계 등)의 시험과 보내지 않은 정상 시험을 이어서 넣어 1~11단계가 모두 제출 기록에 들어가게 합니다. `bundle-notes.json`과 `artifacts/submission.json`은 커밋하지 않습니다.

#### 5-1. 작전실 결과 만들기와 확인

작전실(`/`의 "작전실" 칸)은 요청을 보내지 않고 `/attack-results.json`만 읽어 보여 줍니다. 숫자는 이 파일에 있는 기록을 그대로 센 값이며, 파일이 없거나 형식이 맞지 않으면 숫자를 하나도 표시하지 않습니다. `미실행`과 `미확인`은 요청을 보내지 않은 시험으로 따로 표시하고 성공으로 세지 않습니다.

1. `npm ci`
2. `npm run test:attack && npm run test:ops` — 가상 응답으로 점검기와 작전실 코드를 확인합니다. 실제 배포 결과가 아닙니다.
3. `npm run attack:results` — 실제 배포에 로그인 없는 GET 요청 9건을 보내고 `public/attack-results.json`을 씁니다. 승인된 기기 세션이 필요한 정상 요청은 `ATTACK_CHECK_LOGIN_TOKEN`, `ATTACK_CHECK_DEVICE_TOKEN`을 학생이 직접 환경에 넣었을 때만 보내고, 없으면 `not_run`으로 남습니다.
4. 콘솔에 나온 통과·실패·미실행·미확인 개수를 확인합니다. `fail`이 있으면 해당 항목의 `reason`부터 봅니다.
5. `public/attack-results.json`을 커밋하고 push해 Vercel이 다시 배포하게 합니다.
6. 배포 주소의 `/`를 열어 작전실의 개수가 4에서 본 개수와 같은지 확인합니다.

| | 정상 결과 | 거부되어야 할 결과 |
|---|---|---|
| 작전실 | 결과 파일이 있으면 개수·시험별 상태·HTTP 코드·요청 ID·확인 시각이 파일과 같게 보임. 요청 ID가 없던 시험은 `없음`, 보내지 않은 시험은 `—` | 결과 파일이 없거나 형식이 틀리면 숫자 없이 "실행한 점검 결과가 없습니다" 또는 "표시하지 않습니다" 문구만 보임 |

이 절의 6단계(배포된 화면에서 개수 대조)는 아직 실제 배포에서 하지 않았습니다.

#### 6. 중지

| 하려는 일 | 방법 | 상태 |
|---|---|---|
| 내 세션 끝내기 | 화면의 로그아웃 또는 `POST /api/auth/logout`. 쿠키 두 개를 지우고 기기 세션을 DB에서 회수합니다. | 코드로 확인, 실제 배포 미시험 |
| 한 기기의 접근 끊기 | Supabase에서 `device_credentials`의 `status`를 `approved`가 아닌 값(예: `revoked`)으로 바꿉니다. 서버가 요청마다 승인 상태를 다시 확인하므로 이미 발급된 세션도 다음 요청부터 거부됩니다. | `test:device`(가짜 DB)로 확인, 실제 DB 미시험 |
| 이상 접속 회수 | `detect`의 `propose_revocation`은 제안입니다. 실제 회수는 엔진이 집행하며, 연결 여부는 확인하지 못했습니다. | 미확인 |
| 서비스 전체 멈추기 | 이 저장소에는 중지 스위치가 없습니다. Vercel 프로젝트·배포 설정 화면의 기능을 씁니다. | 미시험 |
| 키가 노출된 것 같을 때 | Supabase에서 서버 전용 키를 새로 발급하고, 새 값을 Vercel 비밀 입력란에만 넣어 다시 배포합니다. | 미시험 |

#### 7. 복구

**코드·배포**: 잘못된 변경은 `git revert <커밋>`으로 되돌립니다. `git reset --hard`는 쓰지 않습니다. 이전 배포로 돌아가는 일은 Vercel의 배포 목록 기능을 씁니다(미시험).

**메모 한 건**: `POST /api/notes/:id/restore`에 `{ "snapshotId": "<UUID>", "contentSha256": "<64자리 소문자 16진수>" }`를 보냅니다. 같은 출처, 로그인, 승인된 기기 세션이 필요합니다. 성공하면 200과 `id`, `ownerId`, `contentSha256`, `auditId`를 돌려줍니다. 실패는 400 `INVALID_RESTORE_INPUT`, 404 `SNAPSHOT_OR_NOTE_NOT_FOUND`, 409 `SNAPSHOT_HASH_MISMATCH`입니다. 스냅샷을 만드는 방법은 이 저장소에 없고, 실제 복구 호출과 복구 후 검증은 아직 하지 않았습니다(10단계 절 참조).

**정책(`src/decider.mjs`의 구역 정책 함수)**: 

```bash
npm run policy:compare   # 사본을 읽고 검증·비교
npm run policy:restore   # 미리보기만 (적용 안 함)
node scripts/restore-policy-backup.mjs --apply --confirm   # 실제 적용
```

사본 `policy-backups/verified-policy.json`과 독립적으로 확인한 신뢰 해시가 모두 있어야 합니다. 지금 저장소에는 사본이 없고 신뢰 해시도 `null`이므로 **복구는 중단되는 것이 정상**입니다. 사본을 임의로 만들거나 과거 커밋을 사본으로 간주하지 않습니다.

#### 8. 지금까지 실제로 확인한 것

학생이 로컬에서 실제 배포 주소로 점검기를 실행해 보고한 표(36개 시험) 기준입니다. 표에는 상태·HTTP 코드·요청 ID만 있었고 확인 시각과 커밋은 없었습니다. 이 표는 쓰기 요청도 보내던 이전 점검기의 결과입니다. 현재 점검기는 GET만 보내므로 같은 숫자가 다시 나오지 않으며, 5-1절의 `public/attack-results.json`을 만들면 이 표의 숫자를 그 파일의 값으로 바꿔 적습니다.

| 상태 | 개수 | 내용 |
|---|---|---|
| `pass` | 20 | 로그인 없는 거부 요청, 다른 출처·잘못된 메서드 거부, 첫 화면의 `nosniff`, `/aleph.json` |
| `fail` | 1 | `anonymous_note_read`(HTTP 200). 이 시험은 1단계의 공개 가상 메모 표시를 찾는데, 현재 `data.json`의 `notes`는 비어 있습니다. 코드상 예상되는 결과이며 실제 `reason` 값은 표에 없어 확인하지 못했습니다. |
| `not_run` | 10 | 세션 값이 없어 보내지 않은 4개, 다른 계정·메모 변경·대량 요청이 필요한 6개 |
| `unverified` | 5 | 6·7·9단계의 엔진·심판 판정은 HTTP로 확인할 수 없음 |

`not_run`과 `unverified`는 요청을 보내지 않았다는 뜻이며 성공으로 세지 않습니다. 이 표는 학생 자신의 점검이고 심판의 판정이 아닙니다.

### 기기 승인 구현 상세

#### 목표

10단계까지는 로그인과 메모 소유권, 이상 접속 판정을 다뤘습니다. 그러나 로그인에 성공하면 어느 기기에서든 메모 API를 호출할 수 있었고, 화면의 "기기 승인" 문구는 서버 상태와 연결되어 있지 않았습니다.

11단계에서는 **관리자가 승인한 기기에서 인증한 경우에만** 서버가 메모 API를 허용하도록 구성합니다. 화면의 표시나 브라우저가 보낸 값이 아니라 서버가 DB에서 확인한 승인 상태를 기준으로 합니다.

#### 구현 내용

##### 1. WebAuthn 기기 등록·인증 API

`api/device/` 아래에 다섯 개의 API를 추가했습니다.

| 경로 | 역할 |
|---|---|
| `POST /api/device/status` | 현재 기기 상태 조회 |
| `POST /api/device/register-options` | 등록 옵션 발급, 5분짜리 일회성 챌린지 저장 |
| `POST /api/device/register-verify` | 등록 응답 검증 후 `pending` 상태로 저장 |
| `POST /api/device/auth-options` | 승인된 자격 증명에 대해서만 인증 옵션 발급 |
| `POST /api/device/auth-verify` | 서명·챌린지·출처·사용자 확인 검증 후 기기 세션 발급 |

- 모든 요청은 `Cache-Control: no-store`, 동일 출처 검사, 학생 로그인 검사를 거칩니다. 심판 토큰은 기기 등록·인증에 쓸 수 없습니다.
- 서버 측 WebAuthn 검증은 `@simplewebauthn/server`가 담당합니다.
- 챌린지는 사용자·용도·만료·미사용 조건을 한 번에 확인하며 소비하므로 재사용할 수 없습니다.

##### 2. 등록은 자동 승인되지 않습니다

등록에 성공해도 자격 증명은 항상 `pending`입니다. 관리자가 Supabase 대시보드에서 `device_credentials`의 `status`를 `approved`로 바꾸고 `approved_by`, `approved_at`을 채워야 승인됩니다. 이 세 값 중 하나라도 없으면 서버는 승인으로 보지 않습니다.

##### 3. 기기 세션과 메모 API 연결

- 인증에 성공하면 무작위 세션 토큰을 만들고, DB에는 SHA-256 해시만 저장합니다.
- 원문 토큰은 `__Host-byte-back-device-session` 쿠키(`HttpOnly; Secure; SameSite=Strict; Path=/`)로만 전달합니다. DB 저장에 실패하면 쿠키를 발급하지 않습니다.
- `api/notes.js`, `api/notes/[id].js`, `api/notes/[id]/restore.js`는 로그인 검증 직후, 메모 DB 작업 전에 `requireApprovedDevice`를 호출합니다. 세션 일치, 사용자 일치, 만료·회수 여부, 자격 증명의 소유자와 승인 상태를 모두 확인하며 조회 오류가 나면 거부합니다.
- 로그아웃하면 로그인 쿠키와 기기 세션 쿠키를 모두 지우고 DB의 세션을 회수합니다.

##### 4. 화면 연결

로그인 직후와 새로고침 직후에 `/api/device/status`를 조회합니다. 서버가 유효한 기기 세션을 확인한 경우에만 메모 영역과 목록을 표시하고, 상태에 따라 `이 기기 등록 요청` 또는 `기기 인증` 버튼을 보여 줍니다. 화면의 상태값은 표시용이며 서버 권한으로 쓰이지 않습니다.

#### 확인 방법

```bash
npm run test:device
```

가상 인증기와 인메모리 DB를 사용해 다음을 확인합니다.

- 비로그인·심판 토큰의 기기 API 호출 거부
- 만료되었거나 이미 사용된 챌린지, 잘못된 서명의 응답 거부
- 등록 성공 후 상태가 `pending`인지, `pending`·`rejected`·`revoked`는 세션을 받지 못하는지
- 승인된 자격 증명만 세션을 받고, DB에는 토큰 해시만 저장되는지
- 만료·회수된 세션, 다른 사용자의 세션, 승인이 해제된 자격 증명, DB 조회 오류에서 메모 접근이 거부되는지
- 기기 세션이 있어도 다른 사용자의 메모 소유권 검사가 유지되는지

#### 보안 개선 결과 및 한계

11단계에서는 로그인만으로 메모를 열 수 있던 구조를, **로그인 + 관리자가 승인한 기기의 서버 세션**이 모두 있어야 열리는 구조로 바꿨습니다. 승인 상태를 해제하면 이미 발급된 세션도 다음 요청부터 거부됩니다.

다만 다음은 확인하지 못했습니다.

- 테스트는 가상 인증기와 가짜 DB를 사용한 로컬 연습입니다. 실제 기기(지문·PIN)와 브라우저에서의 등록·인증은 별도로 확인해야 합니다.
- 실제 Supabase DB와 Vercel 배포에서의 동작, 그리고 심판의 최종 판정은 이 테스트로 증명되지 않습니다.
